A knowledge graph of your codebase that shows where every edge came from

kg is a command-line tool for developers and AI agents. A deterministic parser maps a Python repository's files, modules, functions, imports, dependencies and tests. Your AI agent can add the documents, design decisions and concepts it finds. Both live in one JSON graph in your repo: query it, render it as PNG, SVG or interactive HTML, and trace each fact back to its lines.

How it works

Two sources write the same graph, merged by stable IDs such as module:app.core or decision:use-networkx. kg itself never calls a model: your agent uses it as a tool.

From the code

Deterministic. Seconds. Rerun it whenever the code changes.

  1. kg init

    Creates .kg/graph.json inside the repo.

  2. kg extract .

    Reads .py files with Python's ast (never runs them), plus pyproject.toml and requirements files. Reruns replace the parser's layer and keep what agents added.

  3. kg status --check

    Fails when the code has changed since the last extract, for CI or a pre-commit hook.

From your agent (optional)

Claude Code, Codex or any agent that can run a CLI and write JSON.

  1. kg guide

    Instructions for the agent: what to add, how to cite lines, how to score confidence. Also installable as a skill with kg guide --skill.

  2. kg add agent.json --dry-run --json

    Validates the agent's document. Errors carry a JSON path, the expected value and a suggestion, so the agent can fix them in one pass.

  3. kg add agent.json

    Merges documents, decisions, concepts and issues. Adding the same file twice changes nothing.

One graph, three ways to read it

A NetworkX MultiDiGraph stored as sorted, deterministic JSON that diffs cleanly in git.

kg render --html

One offline HTML file: search, filter by type, click a node for its provenance and relations.

kg query

A node and its neighbours, text search, paths, and code with no test or no document pointing to it.

kg impact

What a change may affect, walking imports, tests, documents and decisions backwards, with the chain of edges behind each result.

Parser edges are facts about the code

Method parser, confidence 1, with the file and line range. Rebuilt on every kg extract, so they follow renames and deletions.

Agent edges are claims with a source

Method llm or manual, a confidence from the guide's rubric and the lines they were read from. kg extract keeps them; nothing regenerates them, so they need review when the code moves on.

Quick start

Python 3.12 or newer, on Linux. kg is not on PyPI yet, so it installs from GitHub.

Install

pipx install git+https://github.com/Cristian1A/kg.git
kg --help

Or pip install git+https://github.com/Cristian1A/kg.git inside a virtual environment. PNG or SVG images of 500 nodes or more also need scipy.

Map your own repository

cd your-python-repo
kg init                         # create .kg/graph.json
kg extract .                    # code, tests, dependencies
kg render --html                # writes kg-graph.html
kg query untested --type Module # modules no test imports
kg query find <name>            # look up node IDs
kg impact <node-id> --brief     # what a change may affect

Then point your agent at kg guide to add documents, decisions and concepts. Every command takes --json. Full instructions: install, quick start and queries.

Or ask a published graph three questions

Rebuild the python-clean-architecture example at the commit it was made from. The agent layer is downloaded from this repository, so no LLM is needed.

git clone https://github.com/wesleey/python-clean-architecture
cd python-clean-architecture  # keep the name: it is the repo's ID
git checkout 6f58de5
kg init && kg extract .
curl -sL https://raw.githubusercontent.com/Cristian1A/kg/main/examples/agent/python-clean-architecture.json \
  | kg add -
kg impact module:src.domain.entities.user --type Module --brief
kg query untested --type Module
kg query node decision:clean-architecture --brief

What we have learned so far

From the MVP validation on four repos, the five example graphs and the benchmark, including the large-repo run on scrapy that ended the project. Each point links to its evidence.

A missing edge is not proof of a missing relation. It may be a relation the parser does not extract, or one no agent has added yet. kg answers say so: an empty result reads “no relation found in the graph”, and every answer lists what it may be missing, such as relation types with no edges or files changed since the last extract (coverage limits).

Observed behaviour

  • The parser covers the structure of a Python repo. Files, packages, modules, classes and functions with signatures and line ranges; internal and external imports; dependencies declared in pyproject.toml or requirements files; and pytest-style tests, with a tests edge to the code they import or refer to. Running it twice leaves the store byte for byte identical. extract.md
  • Agents can write valid graph input on the first try. In the MVP validation, the agent layers of all three external repos passed kg add --dry-run on the first attempt, each element citing its file, lines and a confidence. A deliberately broken document with five typical mistakes was fixed from the error messages alone. MVP validation
  • Provenance lets you check one edge at a time. In the node card at the top, the imports of etl.utils are parser facts you can confirm in etl/utils.py; the decision that it serves the Azure PostgreSQL target is an agent's reading of README line 19, at confidence 0.85. Different sources, different checks. schema.md
  • The agent layer surfaces documentation drift. In my_first_data_project it recorded that the README announces four workflows and lists five, and says etl/__init__.py imports the modules when the file is empty. MVP validation
  • Multi-hop questions are where the graph saves effort. Impact and import-chain questions took fewer tool calls with the graph on six of seven benchmark questions, at the same accuracy. benchmark
  • A stale graph warns instead of guessing. Every benchmark answer over an outdated graph mentioned that it was stale, and none claimed what the graph could not show. benchmark

Current limitations

  • No calls edges. kg impact propagates through imports, so a change to a function reaches the modules that import its module, not only its callers. For the module-level benchmark questions, imports were enough; no function-level question was tested. query.md, RF-13
  • Test detection is a static heuristic. It misses fixtures, code reached indirectly through other calls, and dynamic access. “Untested” means no test refers to it directly. extract.md
  • Python only, and only code and manifests. CI workflow triggers and other configuration are not read by the parser. In the benchmark, the graph repeated a README claim (“flake8 is the only automatic workflow”) that a weekly CodeQL schedule contradicts. benchmark
  • Import names and package names are not reconciled. The node card above shows both dependency:azure (imported) and, through the decision, dependency:azure-storage-blob (declared) as separate nodes. MVP validation, RF-32
  • The agent layer ages. Nothing regenerates it, and the benchmark found a decision citing a line that had since become a different heading. Only a reader that opens the cited lines notices. benchmark
  • A stale graph is safe but expensive. It cannot index files it has not seen, so an agent reads the changed files whole: right answers, three to four times the context of reading the code. keeping the graph fresh

The large-repo test, and what it left open

  • On a repository too large to read, the graph did not beat the code. On scrapy (489 files), an agent with the graph next to search scored 0.96 against 0.98 for reading the code, and took 45% longer. Where it used the graph, it read half as much at the same score; the graph never made an answer more accurate. write-up
  • The parser's gaps cost answers. Imports under TYPE_CHECKING, inheritance and classes loaded from strings in settings are not in the graph, and each was behind a lost answer. Edges from such strings remain an open idea. write-up
  • Not tested: checking documents against code, and an MCP server. Both depended on the large-repo result. roadmap

Benchmark: does the graph help an agent?

The same agent answers questions about a repository by reading the code, or by querying the graph and then reading only the lines it cites. Answers are graded against references checked in the code.

The graph does not beat reading the code. On small repos, node cards (kg query --brief) tied the code's score with 63% less context. On scrapy, the large repository kg was built for, an agent with the graph next to its search tools tied the code's score and took 45% longer. Where it chose the graph, it read half as much; nowhere did the graph make an answer more accurate. Full account: the write-up.

How it was run

  • A fresh Claude Code subagent (Claude Opus 5.5) per question and strategy, 25 tool calls at most, the same prompt apart from the tool section.
  • Repos: the four external examples above (scrapy among them) plus kg itself, and a copy of kg with an outdated graph. 45 questions in all.
  • Mechanical grading: F1 over normalised names, or keyword groups. Traceability: the share of cited evidence that exists in the repo or the graph.
  • Tool output is measured in characters. Token totals are reported too, but about 28 000 of each are Claude Code's own prompt.

Limits of this evidence

  • 16 questions on scrapy, one or two runs per strategy: 0.02 in score is a tie.
  • 14 of the 16 scrapy questions are one-hop lookups; harder impact questions were planned but not run.
  • The same model family wrote the questions, the references and each graph's agent layer, and the agent layer was written with the code at hand.
  • The subagents ran inside this repository, whose AGENTS.md describes kg.

Full report, with every run, the multi-hop questions and the answers to the v0.2 exit questions: docs/benchmark.md. The harness, questions and raw results (bench/results/) are committed, and bench/README.md explains how to rerun it with an Anthropic API key or with a coding agent's subagents.

As of October 2026. The large-repo benchmark ended the project; nothing further is planned.

  • Schema, validation with actionable errors, the .kg/ store, add, remove, edit

  • kg query and kg impact, with --brief node cards
  • kg guide for agents, and the benchmark report

After v0.2

  • The large-repo benchmark ran on scrapy, and its gate failed
  • Faster reads on main: a query on scrapy takes 0.8 s, from 4.9 s
  • Not pursued: checking documents against code, DOT and Mermaid export, an MCP server

Report a problem or contribute

  • Found a bug or want a feature? Open an issue with the bug or feature template, or browse the open issues.
  • Want to change the code? Read CONTRIBUTING.md for commit and branch conventions, and AGENTS.md for the rules AI coding agents follow here. CI runs pytest, ruff and a smoke test of a clean install on every pull request.
  • Want to try it on your repo and tell us what broke? That is the most useful contribution right now: the limits above come from exactly that.
